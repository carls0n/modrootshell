`A simple LKM which gives a rootshell. Also hides module from /sys/module and /prco/modules as well as kernel tracing files`.<br>

\# `git clone https://github.com/carls0n/modrootshell`<br>
\# `cd modrootshell`<br>
\# `make`<br>
\# `sudo insmod modrootshell`<br><br>
`kill -63 8000 [user defined number in source code] toggles module unhide/hide`<br>
`kill -64 31337 [user defined number in source code] gives a rootshell`<br>

`Must have module unhidden to uninstall`<br><br>
`# kill -63 8000 (or whatever number you defined in source code)`<br>
`# sudo rmmod modrootshell`

`In my paper, https://carls0n.github.io, defeating LKM and LD_PRELOAD rootkits for fun and profit, I talked about the impossibility of using ftrace or even kprobes for your LKM and not registering under /sys/kernel/tracing/enabled_functions. Even if we used kprobes and notrace in our code, we could make the registrations under available_filter_functions vanish, hooking sys_kill via kprobes still uses the ftrace backend, which is going to register SOMETHING in enabled_functions.`<br>

`Well...there's more than one way to skin a cat, as they say. There are more options available for hooking sys_kill. In this particular module, we are going to use inline hooking which will use a temporary kprobe registration to locate the non-exported kernel function kallsyms_lookup_name, which then resolves the address of __x64_sys_kill. This method allows us to bypass the ftrace based enabled_functions file. Nothing registered there. Then, we use notrace in our code for our functions, which will successfully hide them from available_filter_functions.`<br>

`Of course, the module starts out hidden. From both /sys/module and /proc/modules. But if we cant detect this thing in neither /sys/kernel/tracing/enabled_functions or /sys/kernel/tracing/available_filter_functions, then how do we find this thing, short of running volatility and looking for it in memory?`<br>

`Actually, it's quite simple if you just know this one trick. Here we are going to get the address of __x64_sys_kill:`

`# sudo grep -w "__x64_sys_kill" /proc/kallsyms`<br>
`ffffffff8fd87790 T __x64_sys_kill`<br>
`Copy this address, just the first series of letters and nummbers`

`Next, type the following:`<br>

`# sudo gdb --core=/proc/kcore`<br>

`[New LWP 1]`
`Core was generated by 'BOOT_IMAGE=/vmlinuz-linux root=UUID=bc34e1d3-da3c-41c1-8555-d0bb0557ba74 rw zsw'.`

`At the prompt, type the following, which should give us the first 5 instructions starting at this address. Using the address we got from kallsyms for __x64_sys_kill. Just put an 0x in front of it.` `That tells gdb that the address is going to be in hexadecimal format.`<br>

`(gdb) x/5i 0xffffffff8fd87790`<br>

   `0xffffffff8fd87790:	movabs $0xffffffffc07c7200,%rax`<br>
   `0xffffffff8fd8779a:	jmp    *%rax`<br>
   `0xffffffff8fd8779c:	mov    $0x1,%esi`<br>
   `0xffffffff8fd877a1:	push   %rbx`<br>
   `0xffffffff8fd877a2:	sub    $0x38,%rsp`<br>
`(gdb)`

`If this is what you have, you found it! This proves beyond a shadow of a doubt that sys_kill is hooked!`<br>
