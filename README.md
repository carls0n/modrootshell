# modrootshell
A simple LKM which gives a rootshell. Also hides module from /sys/module and /prco/modules as well as kernel tracing files.

In my paper, defeating LKM and LD_PRELOAD rootkits for fun and profit, i talked about the impossibility of using ftrace or even kprobes and not registering under /sys/kernel/tracing/enabled_functions. Even if we used kprobes and notrace in our code, we could make the registrations under available_filter_functions vanish, hooking sys_kill via kprobes still uses the ftrace backend, which is going to register SOMETHING in enabled_functions.

Well...there's more than one way to skin a cat, as they say. There are more options available for hooking sys_kill. In this particular module, we are going to use inline hooking which will use a temporary kprobe registration to locate the non-exported kernel function kallsyms_lookup_name, which then resolves the address of __x64_sys_kill. This method allows us to bypass the ftrace based enabled_functions file. Nothing registered there. Then, we use notrace in our code for out functions, which will successfully hide them from available_filter_functions.

Of course, the module starts out hidden. From both /sys/module and /proc/modules. But if we cant detect this thing in neither /sys/kernel/tracing/enabled functions or /sys/kernel/tracing/available_filter_functions, then how do we find this thing, short of running volatility and looking for it in memory?

Actually, it's quite simple if you just know this one trick:

# sudo grep -w "__x64_sys_kill" /proc/kallsyms
ffffffff8fd87790 T __x64_sys_kill

Next, type the following:

# sudo gdb --core=/proc/kcore

[New LWP 1]
Core was generated by `BOOT_IMAGE=/vmlinuz-linux root=UUID=bc34e1d3-da3c-41c1-8555-d0bb0557ba74 rw zsw'.

At the prompt, type the following, which should give us first 5 instructions starting at this address followed by the address we got from kallsyms for __x64_sys_kill. Just put an 0x in front of it. That tells gdb that the address is going to be in hexadecimal format.

(gdb) x/5i 0xffffffff8fd87790

   0xffffffff8fd87790:	movabs $0xffffffffc07c7200,%rax
   0xffffffff8fd8779a:	jmp    *%rax
   0xffffffff8fd8779c:	mov    $0x1,%esi
   0xffffffff8fd877a1:	push   %rbx
   0xffffffff8fd877a2:	sub    $0x38,%rsp
(gdb) 

If this is what you have, you found it! This proves beyond a shadow of a doubt that sys_kill is hooked!

Heres what it SHOULD look like:

   0xffffffff8fd87790:	endbr64
   0xffffffff8fd87794:	call   0xffffffffc07d8000
   0xffffffff8fd87799:	push   %rbp
   0xffffffff8fd8779a:	xor    %edx,%edx
   0xffffffff8fd8779c:	mov    $0x1,%esi
(gdb) 

If you dont have have kcore

# ls -l /proc/kcore

then you will need to download and extract the vmlinuz binary

# wget https://raw.githubusercontent.com/torvalds/linux/master/scripts/extract-vmlinux
# chmod +x extract-vmlinux
# ./extract-vmlinux /boot/vmlinuz-$(uname -r) > vmlinux

if symbols look corrupted or mismatched, calculate the live offset

# sudo grep ' _sdata' /proc/kallsyms

(gdb) add-symbol-file ./vmlinux <address_of__sdata_found_above>
